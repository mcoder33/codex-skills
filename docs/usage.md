# Примеры использования

[К обзору](../README.md) · [Установка](installation.md)

Примеры ниже — запросы в чат Codex, не команды shell. Замените учебные задачи своими. Для первого вызова не требуется включать навык глобально.

## Настроить общение

```text
$adaptive-dialogue Сначала давай вывод, потом основания.
Для обычных правок отвечай коротко, для архитектурных решений объясняй
компромиссы. Учитывай мои поправки в следующих ответах.
```

Проверьте следующий содержательный ответ: изменились ли порядок и глубина, сохранились ли ограничения. Навык использует существующую разрешённую память; его установка не создаёт хранилище предпочтений.

## Ясно изложить результат

```text
$clear-communication Объясни результаты локального замера:
ошибок стало 100 вместо 200, а запросов — 2 тысячи вместо 10 тысяч.
Покажи, как изменились количество и доля ошибок, сохрани ограничения.
```

Ожидайте различение количества и доли: ошибок меньше, но доля выросла с 2% до 5%. Вывод должен сохранить условия замера; он не доказывает production-готовность. Ориентир «80%» допускает гибкость формы, сохраняя факты и ограничения. HTML и презентации создаются по запросу. [Сценарии](../skills/clear-communication/references/scenarios.md) и [границы проверки](clear-communication-validation.md).

## Разобраться в проблеме

```text
$dialogue-explore Хотим сократить время подготовки еженедельного отчёта.
Сейчас три человека собирают данные вручную. Помоги понять, что стоит
автоматизировать первым. Карту сохраняй в разрешённом vault по пути …
```

Ожидайте ближайший существенный вопрос, затем следующий шаг с учётом ответа. В карте должны различаться цель, варианты, принятые решения и открытые вопросы. Конкретное поручение на реализацию не требует предварительного интервью.

После паузы попросите: «Восстанови по карте принятые решения и ближайший открытый вопрос». Проверьте, что восстановление опирается на сохранённую заметку и предложение не стало принятым решением без вашего ответа.

## Проверить готовый план

```text
$dialogue-validate План: автоматизируем выгрузку данных,
потом расчёт показателей, затем отправку отчёта.
Проверим зависимости, критерии правильности и сценарии отказа.
```

Ожидайте последовательную проверку оснований. Итог должен показывать, что подтверждено, какие проверки только предложены и что ещё мешает реализации. Обсуждение не равно запуску тестов или разрешению отправлять отчёт другим людям.

## Оценить инженерную готовность

```text
$nasa Нужно добавить скидки в сервис заказов. Цена должна воспроизводиться
при повторном расчёте; старые заказы не должны измениться.
Свяжи требования, решения, допущения и проверки.
Покажи, что ещё способно изменить результат реализации.
```

Ожидаемый результат — инженерная карта с критериями результата и основаниями решений. Навык полезен при существенной неопределённости; он не превращает количество ответов в вероятность успеха и не подтверждает соответствие стандартам NASA. [Источники метода](../skills/nasa/references/sources.md).

## Разработать или проверить Go-код

```text
$go-development Проверь обработку отмены заказа в этом Go-репозитории.
Проследи операцию от входа до сохранения результата. Пока только ревью:
покажи дефекты, затронутые границы и подходящие проверки.
```

Для реализации задайте поведение и объём:

```text
$go-development Исправь повторную отмену заказа:
она должна возвращать прежний результат и не повторять списание.
Добавь проверку этого сценария и покажи результат.
```

Для обычной правки достаточно лёгкой проверки; существенная структурная работа требует сравнения и проверки поведения. Смотрите, завершена ли вся согласованная операция. Навык не требует фиксированного размера функций и не навязывает DDD. При изменениях ownership, goroutines и shutdown проследите владельцев данных, отмену и фактическое завершение работы. Зелёный race test сам по себе не исключает логическую гонку. [Проверки версии](go-development-validation.md), [маршрут чтения](../skills/go-development/references/reading-paths.md) и [протокол разрешённой совместной работы](../skills/go-development/references/agent-workflow.md).

## Проверить Grafana

```text
$grafana-dashboards Проведи аудит приложенного dashboard JSON.
Экран должен отвечать, поступают ли события и успевает ли обработка.
Проверь временные окна, единицы, фильтры и отсутствие данных.
Пока ничего не сохраняй в Grafana.
```

Для изменения добавьте целевое поведение и разрешённую область записи. Ожидайте проверку актуального JSON, смысла запросов и доступных данных. Визуальная проверка требует UI или renderer; отсутствие доступа должно остаться в отчёте. Зелёная панель сама по себе не доказывает полноту данных. [Сценарии проверки](../skills/grafana-dashboards/references/acceptance-scenarios.md).

## Выбрать исполнителя

`model-router` задаёт политику выбора модели и контракт работы. Нужны поддержка подагентов и разрешение на делегацию в текущей среде.

```text
$model-router Для этой согласованной задачи разрешаю делегацию.
Выбери доступного исполнителя, задай область изменений,
критерии результата и проверки. Верни итог в этот чат.
```

Проверьте, что исполнитель получил цель, файлы, ограничения и критерии завершения. Передача не отменяет обязательные стадии проекта. Главный агент сообщает фактический результат и ограничения; установка навыка сама по себе не разрешает делегацию.

## Статистика и улучшение навыков

- Для `delegation-stats` сначала прочитайте [настройку и формулы](telemetry.md). Отчёт строится по доступным локальным событиям; неполнота данных должна быть отмечена, API-сценарий не является фактическим списанием.
- Для `session-retrospective` используйте [отдельное руководство](retrospective.md). Без разрешения на автоприменение допустимы предложения. Изменения ограничены двумя dialogue-навыками и требуют поведенческих проверок и независимого ревью. Результат «ничего не менять» допустим.

## Как понять, что навык работает

Проверяйте на небольшой реальной задаче: клиент обнаружил навык, результат соответствует запросу, ограничения сохранены, обещанные файлы записаны. Для карты откройте заметку; для кода прочитайте diff и результат проверки; для Grafana проверьте данные и экран.

Запишите версию навыка, запрос и конкретное наблюдение в своём хранилище. Загрузка `SKILL.md` подтверждает только загрузку; пользу оценивают по результату задачи и последующим поправкам.

## Оркестратор для одной задачи

`$orchestrate Проверь обработку ошибок и исправь подтверждённые дефекты.`

Главный агент распределяет работу и выбирает модели по сложности. Навык включается только явно; обычное «делай» его не активирует. После завершения задачи режим прекращается. «Дальше без оркестратора» отключает его досрочно.
