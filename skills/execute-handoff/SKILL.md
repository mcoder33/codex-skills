# Передача работы по команде «делай»

Главный агент сохраняет диалог и передаёт согласованную работу одному исполнителю. Пользователю не нужно составлять промпт, переносить контекст или переключать модель основного чата. Навык применяется главным агентом; исполнитель не запускает его рекурсивно.

## Вход и контракт

Определи намерение по контексту: «делай», «приступай», «реализуй» после согласования задачи означают переход к исполнению. Вопрос «как будет работать команда делай?» и цитата не являются запуском. При нескольких нерешённых вариантах уточни выбор; не используй таймер для разрешения неоднозначности задачи.

Собери компактное самостоятельное задание: цель, ожидаемое поведение, принятые решения и их основания, проверенные факты с путями/источниками, открытые пробелы, ограничения, область владения файлами, критерии завершения и проверки. Различай решение пользователя и гипотезу агента. Укажи, что исполнитель не один в рабочей области и должен сохранять чужие изменения. Не передавай всю историю автоматически и не заставляй исполнителя повторять уже подтверждённое исследование.

Сохрани обязательный workflow проекта и ограничения роли. Этот навык добавляет передачу и выбор модели, не отменяя требуемые стадии реализации/ревью. Разрешение на делегацию ограничено текущей согласованной задачей; оно не разрешает релиз, merge или внешнюю коммуникацию само по себе.

## Предложение модели

Проверь доступные в текущем runtime модели, reasoning и роли. Эвристика при отсутствии явного выбора:

- Обычная реализация с ясным результатом — Sol medium.
- Узкая понятная работа с простой проверкой — Luna high.
- Сложная реализация или критическое ревью — Sol high.

Используй точный доступный ID, а не предполагаемый алиас. Для Luna, изменяющей файлы, выбери роль с правом изменения; read-only scout не подходит. Фиксированные параметры роли могут перекрывать defaults и overrides. Не меняй модель основного чата и не редактируй конфигурацию ради одного запуска. Недоступную пару не заменяй молча: предложи доступную и снова открой выбор.

## Окно выбора — 30 секунд

Автоматический выбор по таймеру допускается только при предварительном явном разрешении пользователя на этот режим (в текущем разговоре или применимых инструкциях). Установка навыка сама по себе такого разрешения не даёт. Без него запроси выбор и жди ответа. Истёкшее время не является ответом или согласием.

В разрешённом режиме это необязательная возможность изменить уже разрешённый выбор по умолчанию, а не обязательное approval. До запуска:

1. Через доступный асинхронный инструмент вопросов покажи модель, reasoning, короткую причину и правило: «По умолчанию Sol medium: реализация по согласованному плану. Можно подтвердить сейчас, выбрать другую пару или написать стоп. Если за 30 секунд ответа нет, использую этот заранее разрешённый вариант». Названия и причину подставь по задаче. Если инструмент вопросов отсутствует, используй сообщение только когда runtime явно поддерживает получение новых сообщений во время ожидания.
2. После показа предложения зафиксируй реальное начало и срок 30 секунд доступными часами. Оставайся в активном ходе. Используй прерываемое ожидание, например clock.sleep, не более оставшегося интервала. Не запускай исполнителя до ответа или истечения срока. Не завершай ход финальным сообщением в расчёте на фоновый таймер.
3. При раннем ответе: подтверждение запускает предложенную пару сразу; явно выбранная доступная пара запускается без повторного подтверждения; «стоп», отмена или новый существенный вопрос отменяют автозапуск. Непонятный ответ требует уточнения и приостанавливает таймер. Не трактуй прерванное ожидание как истечение срока: прочитай сообщение и проверь время.
4. При отсутствии ответа после измеренных 30 секунд ещё раз учти все доставленные сообщения и используй заранее объявленную пару. Сообщи «Окно выбора истекло; запускаю Sol medium по заранее разрешённому варианту», не «пользователь подтвердил».
5. Если среда не умеет ждать с приёмом сообщений или ход был завершён/перезапущен, не обещай автозапуск. Сообщи ограничение; при возобновлении открой новое окно, не запускай работу по старому сроку. Это поведение активного агента, не scheduler, hook или фоновый процесс.

Отдельные обязательные разрешения всегда остаются обязательными. Таймер выбирает только модель/effort для уже разрешённой задачи. Если инструкции более высокого приоритета требуют явного ответа на конкретный выбор, жди его без автоматического продолжения.

## Запуск и приёмка

Перед запуском сверь пару с фактическим профилем. При API с ограничением overrides на новый контекст используй fork_turns="none" и самостоятельный контракт. Используй доступную обязательную роль проекта; резервный профиль не отменяет её ограничений. Запроси сообщения о существенном результате и блокере через send_message, если он доступен. Один исполнитель по умолчанию; дополнительные агенты — только по применимому workflow или отдельному разрешению.

Не называй запрошенную модель фактически подтверждённой, если runtime показывает только запрос или статическую конфигурацию. При недоступной делегации сообщи ограничение; не подменяй её запуском CLI, новым чатом или фоновым сервисом.

Проверь полученный результат по согласованным критериям и фактическим артефактам. При исправимых замечаниях верни их тому же исполнителю в рамках задачи; новый заход должен иметь конкретное основание. Смена модели/effort требует нового окна выбора; исправления тем же исполнителем его не повторяют. При повторении того же блокера без новых фактов останови цикл и сообщи, что нужно для продолжения.

Позднее изменение выбора после запуска не игнорируй: останови дальнейшую делегацию, выясни фактическое состояние исполнителя, по возможности прерви его; сохрани уже сделанные изменения и не запускай конкурирующего писателя. Не обещай отмену уже завершённого действия.

Верни в основной чат результат, проверки и существенные ограничения. Различай предложенную пару, выбор пользователя/заранее разрешённый default, запрос запуска и фактическое подтверждение runtime. Сохраняй состояние существующим механизмом памяти, если он предусмотрен; новый журнал или фоновую автоматизацию навык не создаёт.

При изменении навыка проверь сценарии в [references/scenarios.md](references/scenarios.md). Они проверяют решения, а не доказывают надёжность доставки сообщений конкретным клиентом.
