# Основания и пределы навыка

## Уточнение цели в версии 0.2.0

К существующим критериям добавлена явная цель: читать сам код как граф
небольших смысловых узлов, переходя по функциям, файлам и каталогам.
Это уточнённое требование к способу чтения; оно не требует визуализации.
Протокол маршрута и распределение ролей — инженерное предложение для этой
цели, а не новый эмпирически подтверждённый эффект. Пилоты ниже относятся
к исходной версии и не доказывают эффективность нового протокола роя.

## Что произошло в пилоте

Основание — три последовательных цикла на одном серверном приложении и
прямые уточнения его владельца. Полные рабочие отчёты и обсуждения остаются
в приватном хранилище. Здесь приведены обобщённые наблюдения без данных проекта.

- В первом цикле ставка на имена/раскладку была пересмотрена после требования
  одного уровня абстракции. Переходы между файлами исключили из штрафов.
  Новый сценарий стал композицией завершённых операций; читатели-модели
  предпочли его.
- Во втором цикле проверка углубилась в дочерние операции. Выделили полные
  правила значений; независимый читатель обнаружил смешение уровней внутри
  оставшегося без изменения sanitizer.
- В третьем цикле проверили связный путь: допуск snapshot, локальную
  пригодность для attribution, wire projection и JSON mechanics.
  Характеризационные тесты прошли на baseline/candidate; независимое ревью
  не выявило регрессий.
- Важная неудача процесса: исполнитель ограничил широкое ожидание владельца
  одним путём и объявил завершение. Остальные области приложения не прошли
  тот же аудит. Отсюда карта покрытия и различение завершённой итерации
  и завершённого запроса.
- Операционный сбой: два Make в одном checkout одновременно пересоздавали
  vendor. Последовательный прогон прошёл. Вывод относится к конкурирующей
  изменяемой подготовке, а не запрещает любую параллельность.

Наблюдались успешные проверки поведения и предпочтения моделей. Скорость
и точность чтения людьми не измерялись; перенос на другие языки и проекты
этим пилотом не доказан. Принципы ниже сохраняют эти ограничения.

## Первичные источники

- [Martin — One Thing: Extract till you Drop](https://sites.google.com/site/unclebobconsultingllc/one-thing-extract-till-you-drop):
  декомпозиция продолжается в дочерних операциях; несколько инструкций могут
  составлять одно завершённое действие.
- [Martin — Inverse Scope Law](https://www.informit.com/articles/article.aspx?p=1323426):
  имя должно давать читателю смысл вызова.
- [Martin — First Principles](https://www.informit.com/articles/article.aspx?p=3222335):
  небольшие именованные действия и последовательное раскрытие деталей.
- [Evans — DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf):
  язык внутри bounded context, intention-revealing interfaces, связные модули,
  постусловия и инварианты.
- [Vernon — Effective Aggregate Design](https://www.dddcommunity.org/library/vernon_2011/):
  реальные consistency boundaries определяют агрегаты.
- [Siegmund et al., FSE 2017](https://www.cs.cmu.edu/~ckaestne/pdf/fse17.pdf):
  смысловые ориентиры; небольшая выборка, не измерение нашего Go-кода.
- [Scalabrino et al.](https://sscalabrino.github.io/files/2019/TSE2019AutomaticallyAssessingCode.pdf):
  индивидуальные статические метрики не заменяют проверку понимания.

Авторские предписания, эмпирические исследования, пользовательский стиль
и результаты модельного пилота — разные основания. Не превращай их в обещание
универсальной оптимальности. Для исторического пилота полные книги не перечитывались; это ограничение
относится к той версии и её доказательствам.

Для обычной разработки не нужно заново читать все источники. Обращайся к ним
при спорном принципе или новом исследовательском запросе; ищи первичные тексты,
сохраняй ограничения переноса и не подменяй проверку кода авторитетом автора.


## Go Development 0.3.0: источники и фильтр переноса

Переименование и Go-специализация выполнены по прямому запросу пользователя.
Сохранены критерии законченных операций и покрытия0.2.0; ниже добавлена инженерная
синтезация материалов, а не результат нового эксперимента на людях.

**Ultimate Go Notebook**, William Kennedy with Hoanh An, First Edition v1.0,
Ardan Labs Press,2021, Patch41, ISBN978-1-7373844-1-0. Использован предоставленный
пользователем экземпляр. Книга и длинные выдержки в пакет не включены. Номера ниже —
печатные, не номера PDF:

- Гл.1, с.10–24: конкретные данные/прототип, приоритет корректности, читаемость,
  стоимость абстракций, lifecycle и backpressure.
- Гл.2–4, с.25–89: zero values, value/pointer semantics, slices/aliasing,
  embedding и method sets. Runtime layouts/escape — модели для конкретной версии.
- Гл.5, с.90–118: composition, обнаружение интерфейсов, ownership интерфейса,
  precise APIs и ошибки как часть основного пути.
- Гл.6–8, с.119–173: synchronization, channel patterns, cancellation, tests и
  проверка достоверности benchmark. Примеры не являются готовым delivery protocol.
- Гл.9, с.174–199: generics как инструмент типизированного алгоритма/контейнера.
  Текст написан до стабильного Go1.18; проектные примеры требуют проверки компилятором.
- Гл.10–13, с.200–265: pprof, escape/inlining diagnostics, runtime trace,
  tradeoff memory/throughput, stack traces и ABI.
- Гл.14, с.266–350: повторное развитие pointer/escape, OS/Go scheduling,
  CPU/I/O concurrency и GC. Числа и runtime детали не являются нормативными SLA.

При подготовке охвачены объяснения всех глав, примеры изучались выборочно;
все листинги книги не исполнялись и постраничная визуальная проверка не заявляется.
В пакет включены собственные краткие критерии решений, не конспект всей книги.

**Ardan service:** [репозиторий](https://github.com/ardanlabs/service),
[Project Structure](https://github.com/ardanlabs/service/wiki/Project-Structure),
[Package Oriented Design](https://www.ardanlabs.com/blog/2017/02/package-oriented-design.html).
Явные зависимости и предметные обязанности полезны; дерево и названия — пример.
Книга Notebook сама не предписывает эту современную раскладку или Kubernetes.

**Авторитет для языка и runtime:**
- [Go specification](https://go.dev/ref/spec): maps, nil, constraints, method sets.
- [Go memory model](https://go.dev/ref/mem): synchronization, а не временные догадки.
- [Go1.18 release notes](https://go.dev/doc/go1.18): выпущенные generics отличаются
  от предварительных примеров; доступ к общему полю через type parameter не следовал
  автоматически из списка struct types.
- [Go1.22 release notes](https://go.dev/doc/go1.22): изменения loop variables;
  учитывать язык модуля, не копировать shadowing из старого примера механически.
- [GC guide](https://go.dev/doc/gc-guide): современная модель затрат, soft memory limit,
  ограничения переноса heap measurements на process memory.
- [Container-aware GOMAXPROCS](https://go.dev/blog/container-aware-gomaxprocs): версии,
  quotas и runtime defaults; число P не равно числу всех OS threads.
- [Diagnostics](https://go.dev/doc/diagnostics): выбор profiling/tracing средств.

**Kubernetes**, только когда входит в задачу:
[probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/),
[lifecycle hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/).
Это самостоятельные эксплуатационные требования, не следствие дерева Go-пакетов.

## Что намеренно не стало правилом

- Любой interface обязательно выделяет heap memory; любой указатель обязательно escape.
- Запрет копировать всё, на что когда-либо был указатель, или запрет любых getters.
- Read of nil map всегда паникует; capacity=1 оптимально для любого канала.
- Unbuffered send доказывает завершение обработки; нет data race значит нет logical race.
- Число CPU автоматически задаёт размер I/O pool; нулевая allocation цель любой задачи.
- Учебные значения GC%, STW, buffer size или benchmark speedup универсальны.
- Go-рефакторинг требует переехать на Kubernetes или повторить все папки Ardan.

Эти выводы заменены проверяемыми контрактами и version-aware критериями. При новой
спорной детали читай актуальную первичную документацию/код и проверяй минимальный пример
на toolchain проекта. Авторитет автора не заменяет correctness proof.
