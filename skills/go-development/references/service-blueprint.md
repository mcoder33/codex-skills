# Стандартные решения для нового Go-сервиса

Используй при старте проекта и выборе механизма для новой границы. Это переносимый
опыт сервисов преобразования событий и сервисов с журналом доставки. Реализации
дают проверяемые примеры, а не гарантию пригодности для другой нагрузки.

## Выбор основы

| Поверхность | Рабочая основа | Когда менять или опускать |
|---|---|---|
| Сборка приложения | `cmd/<service>` → bootstrap → сценарии → adapters; domain хранит чистые правила | Маленькой утилите достаточно меньшего числа пакетов |
| Конфигурация | Типизированный env config, префикс сервиса, проверка диапазонов и сочетаний до старта | Выбранный проектом формат сохраняется; секреты отдельно |
| CLI | `--help` и `validate-config` без БД/брокера; recovery отдельной командой | Recovery нужен лишь при наличии сохранённой работы |
| Kafka | franz-go как исходный кандидат; отдельные connection options и group/producer options | Зависимость и версию проверять в целевом проекте; не навязывать transport |
| PostgreSQL | pgx/pool, явные транзакции и bounded queries | Для другого хранилища сохранить смысл атомарности и лимитов |
| Логи | `slog`, структурированные события, безопасные поля, JSONL/stdout по среде | Существующий logger адаптировать, не переписывать ради названия |
| Проверки и сборка | Единый Make/CI путь, закреплённый toolchain, воспроизводимый образ | Vendor и генераторы только при принятой необходимости |

Не импортируй приложение целиком ради helper. Общий версионированный модуль должен
содержать действительно общие transport/encoding механизмы и согласованные контракты,
не бизнес-правила двух сервисов. Проверяй границы imports автоматически, если это
существенная архитектурная гарантия. Не копируй приватные module paths в новый шаблон.

## Вход, identity и подтверждение

До реализации выпиши: что означает accepted, что переживает restart, когда разрешён
input commit и какой результат обязан подтвердить получатель. Для Kafka различай
координаты исходного события, текущий offset и trace ID: trace не заменяет identity.
Версионируй wire envelope, проверяй origin, размеры и формат на входе. Декодируй один раз;
передавай проверенные значения с определённым ownership. Синтетические fixtures нужны
по обе стороны границы producer/consumer, включая malformed и несовместимую версию.

Для требования переживать crash используй durable acceptance перед подтверждением
входа. Если бизнес-изменение и отправка должны быть атомарны — transactional outbox
в той же транзакционной границе. Для простого преобразования может хватить downstream
ACK перед commit. RAM enqueue до commit допустим лишь при явно принятой возможности
потери; существующая реализация такого пути не делает его стандартом надёжности.

При журнале сохраняй identity, контроль содержимого, выбранный маршрут и готовые bytes.
Точный повтор читает сохранённый результат до дорогой подготовки и ожидания новой
ёмкости; конфликт содержимого не перезаписывает принятое событие. Изменение правил
не должно незаметно менять ранее принятую доставку. Lease и fencing защищают завершение
claim от старого worker; повтор после ACK до записи completion всё равно возможен.
Receiver dedup/idempotency — отдельный контракт, не следствие наличия outbox.

## Batching и параллельная обработка

Ограничивай batch одновременно числом записей, bytes и возрастом старейшей записи.
Неполная пачка должна flush-иться по времени и при штатном завершении входа.
Общий бюджет учитывает queued, active, retries и completed-waiting-commit; fetch buffers,
producer buffers, DB pools и накладные расходы добавляются к памяти приложения.

Результаты batch сохраняют соответствие каждому входу. ACK успешного соседа не отменяется
из-за ошибки другого; повторяй только failed/unattempted согласно контракту. Отсутствующий
или неоднозначный receipt не является успехом. Для Kafka producer исходный вариант —
all-ISR ACK и idempotent producer, с bounded buffers/deadlines. Это не end-to-end exactly-once.
Linger и размеры пачек выбирай измерением; обход дефекта конкретной версии не универсален.

При параллельной обработке partition commit выполняет один координатор по завершённому
префиксу порядка полученных записей, а не по максимальному завершённому offset. Числовые
пропуски Kafka offsets допустимы. Старый assignment не меняет новый; revoke и lost имеют
разные правила commit. Подробности: [конкурентность](concurrency.md).

## Конфигурация, БД и HTTP

Проверяй связанные бюджеты: concurrency × replicas × pools, batch bytes относительно
лимитов транспорта, send deadline относительно lease и shutdown grace. Неверное значение
должно давать безопасную ошибку до запуска workers. `validate-config` проверяет локальные
инварианты; доступность и права внешних систем проверяются отдельно.

Для обновляемых правил используй согласованный immutable snapshot с возрастом/версией.
После долгого ожидания capacity проверь актуальность перед новым решением; replay уже
принятого результата не пересчитывается. Политика stale config должна быть явной.

Bulk lookup и set-based запись полезны при доказанном N+1. Сохраняй исход каждого элемента,
атомарность нужного поднабора и видимость конкурентных конфликтов. Не держи SQL-транзакцию
или DB lock во время внешнего HTTP. Nullable, integer precision и пустой объект/массив
остаются частью контракта, особенно при переносе из другого языка.

HTTP-клиенты переиспользуются; ограничиваются body/response, соединения и время попытки.
Ожидание admission и сетевой timeout — разные бюджеты. Retry классифицирует временную,
постоянную ошибку и неизвестный исход. Не повторяй внешний эффект лишь потому, что истёк
timeout. Quarantine для неподходящего входа и exhausted для исчерпанной доставки различны;
ручной recovery сохраняет identity, route и payload, имеет явную область и результат.

## Наблюдаемость и остановка

Записывай stage/outcome/duration, безопасные error codes, correlation ID. Измеряй отдельно
input age, ожидание очереди, обработку, транспортный ACK и commit; возраст до чтения не
доказывает медленную обработку внутри сервиса. Backlog count без oldest age скрывает зависание.
Добавляй saturation, retries/exhausted, pool waits и runtime memory/GC по необходимости.
У counters указывай смысл: cumulative или delta/window; restart различай по process/boot ID.
Не используй event IDs и пользовательские значения как неограниченные metric labels.

Обычные логи не содержат тела, телефоны, credentials, SQL args или сырые ошибки драйвера.
Диагностический body dump, если нужен, отделён от общего потока: явное включение,
маскирование, ограничение размера/срока/доступа. Наличие recorder в старом сервисе не
обязывает включать его по умолчанию в новом. Доставка логов может отставать от обработки.

Health подтверждает только заявленную проверку. Разделяй процесс жив, зависимости готовы
и бизнес-поток движется. Для длинного pipeline проверяй свежий сквозной синтетический
результат в разрешённом окружении; HTTP 200 health не заменяет delivery evidence.

Остановка сначала запрещает новый intake, затем drains или безопасно отменяет принятую
работу, joins владельцев и закрывает ресурсы. Intake context и delivery lifetime могут
различаться: отмена первого не должна случайно оборвать обязательный drain. Учитывай
queued, active и delayed retry, последнюю пачку и общий конечный бюджет остановки.
Fatal error одной обязательной петли останавливает peers и доходит до main.

## Проверка и поставка

Минимальный сквозной тест нового сервиса проходит через реальные adapters на синтетических
зависимостях. Для delivery добавь сценарии повторов, partial ACK, crash window, full queue,
rebalance и shutdown ровно на используемых границах. Race detector дополняет проверку
логических инвариантов. Межсервисный handoff проверяй с immutable image другого сервиса,
а не только с собственной копией DTO. [Методика измерений](testing-performance.md).

Единый штатный путь проверяет формат/тесты/vet/lint, зависимости, генерацию и imports по
потребности проекта. Изолируй Compose project, volumes, ports и теги тестовых образов.
Измеряй throughput вместе с latency, памятью и downstream saturation; не переноси числа
workers, queue или pools из другого сервиса без проверки.

Разделяй публикацию версии и deployment. Артефакт связан с source SHA; preflight проверяет
config и совместимость схемы до переключения. Rollback приложения не откатывает данные
и уже выполненные эффекты. Для непрерывного сервиса способ переключения должен сохранять
обработку: recreate единственного экземпляра не является доказанным zero-downtime путём.
Публикация образа, migration и production cutover остаются в пределах поручения.

## Контроль применения

- Небольшой HTTP read-only сервис: config, shutdown, safe logs и проверки; Kafka/outbox не добавляются.
- Kafka → внешний эффект с требованием восстановления: identity, durable/ACK boundary,
  bounded processing, повтор и crash-тест; один зелёный happy path недостаточен.
- Перенос legacy: characterization и совместимость данных; улучшение семантики отдельно согласуется.
- Узкая правка существующего сервиса: затронутый контракт; справочник не запускает полный redesign.

При накоплении нового опыта добавляй решение вместе с условием применения, ограничением
и проверкой. Приватные инциденты, адреса, payloads и окружение остаются вне переносимого навыка.
