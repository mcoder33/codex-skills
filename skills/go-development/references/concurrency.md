# Конкурентность и границы завершения

Читать при изменении goroutines, каналов, shared state, очередей, retries и отмены.
Не перепроектируй работающий scheduler/pool ради применения всех пунктов.

## Что выполняется одновременно

Различай concurrency и parallelism. Определи, где порядок неважен, где обязателен,
каков результат и как объединяются частичные результаты. Async fetch не доказывает
параллельность обработки или commit. Число клиентов, партиций, batches, HTTP-запросов
и delivery workers — разные оси; найди ограничитель на нужной стадии.

Для нового алгоритма полезен корректный последовательный контроль. У существующей
конкурентной системы сохраняй требуемые порядки и предельные нагрузки. CPU-bound и
I/O-bound работа имеют разные причины ожидания: `GOMAXPROCS` не задаёт число всех
OS threads, соединений или допустимых I/O workers. Подбирай concurrency по бюджету
ресурсов и измерению, включая downstream capacity.

## Владельцы, инварианты, сигналы

Для каждой изменяемой goroutine/группы найди:
- кто запускает и владеет её lifetime;
- от чего она блокируется и как выходит при отмене/ошибке/shutdown;
- кто ждёт её завершения и когда можно освободить используемые ресурсы.

Для канала объясни сигнал и результат, отправителя/получателя, capacity и владельца
close. «Send завершился» не равно «работа сделана». Даже unbuffered rendezvous не
доказывает завершение кода receiver или внешний ACK. Для результата нужен отдельный
receipt/outcome либо другая явная синхронизация.

Send синхронизирован до завершения соответствующего receive; для unbuffered receive
также синхронизирован до завершения send. Close синхронизирован до receive, вернувшего
zero из-за закрытия. Эти правила не упорядочивают произвольный код после обеих операций.
Закрытый buffered канал сначала выдаёт оставшиеся значения; send в закрытый канал паникует.

Обоснованный буфер снижает блокировку, но удерживает данные и отодвигает backpressure.
Выбирай минимальную достаточную ёмкость по нагрузке/бюджету; capacity=1 не универсальный
ответ. Для потокового входа считай queued + active + retries + client buffers, а не
только длину channel. Число записей не ограничивает bytes при переменных payload.

Semaphore, захватываемый уже внутри goroutine, ограничивает активную работу, но не число
созданных ожидающих goroutines. Для неограниченного потока ограничивай admission до
создания работы или используй bounded workers. `sync.Pool` не служит очередью, лимитом
ресурсов или надёжным хранилищем; lifecycle значений должен оставаться корректным без него.

## Synchronization и логические гонки

Mutex защищает инвариант целиком, не только отдельные read и write. Два безопасных
доступа по отдельности не делают read–modify–write атомарным. Race detector может быть
зелёным при lost update, двойном внешнем эффекте или ошибке протокола.

Используй mutex для согласованности связанных полей, atomic для подходящей единичной
операции/публикации, channels для координации по смыслу. RWMutex/atomic не автоматически
быстрее обычного mutex. Не предполагается FIFO/fairness сверх документированного контракта.
Не держи lock вокруг долгого I/O без обоснования и не разноси Lock/Unlock так, чтобы владелец
инварианта стал неясен. «Два Lock в функции» — повод разобраться, не автоматический дефект.

## Cancellation, deadline и cleanup

`ctx.Done()` — сигнал, не join. Отмена ожидания не доказывает остановку дочернего I/O.
Передавай caller context вниз; создавай новый timeout там, где есть реальный бюджет
операции. Различай ожидание capacity, время сетевой попытки, общий request deadline
и lifetime partition assignment. Не добавляй короткий I/O timeout на весь pipeline.

У любой потенциально блокирующей операции должен быть обоснованный путь завершения.
`select` с ready cancellation не гарантирует приоритет отмены над готовым send; если
нельзя допустить работу после остановки, синхронизируй admission/shutdown как протокол.

Return caller при timeout не разрешает переиспользовать payload, вернуть buffer в pool,
освободить reservation или закрыть producer, пока нижний слой ещё работает с ресурсом.
Buffered result channel может убрать blocked send, но не отменяет работу и не решает
владение данными автоматически. У неотменяемого I/O обозначь ограничение и bound.

Остановка процесса: прекратить новый приём → завершить/безопасно отменить принятые
операции → дождаться владельцев ресурсов → закрыть ресурсы. Порядок зависит от
контракта; `defer` не исполняется после `os.Exit`. Не заменяй ожидание произвольным sleep.

## Подтверждения, повторы и перегрузка

Различай принятие HTTP-запроса, RAM enqueue, durable write, broker ACK, input commit
и business outcome. Не меняй эту границу рефакторингом или сменой способа развёртывания.
Backpressure переносится на upstream контролируемо: отказ до приёма, pause/resume,
ограниченное ожидание. Drop учебного примера нельзя применять к уже подтверждённой работе.

Если система использует ordered commits, подтверждать можно только непрерывный завершённый
префикс. Поздние результаты после rebalance/смены владельца требуют действующего fencing
или другого принятого механизма. ACK→commit window может допускать повтор; не обещай
exactly-once по наличию канала, Kafka или retry. Retry должен иметь классификацию ошибок,
бюджет и учёт неизвестного исхода; идемпотентность обосновывается внешним контрактом.

Проверяй затронутые границы: full queue, cancellation до/после enqueue, во время I/O,
частичный результат, late receipt, rebalance, close/send, restart и shutdown под нагрузкой.
Используй barriers/каналы/управляемые fakes для воспроизводимого порядка; polling/sleeps
оставляй для реальных асинхронных интеграций с ограничением времени и диагностикой.
