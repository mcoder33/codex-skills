# Go-дизайн: данные определяют границы

Читать при проектировании или изменении пакетов/API, моделей, интерфейсов, generics,
владения и ошибок. Это критерии решения, не обязательный новый слой для каждой функции.

## Пакет и API

- У пакета есть самостоятельная обязанность и понятные потребители. Пакет — граница
  инкапсуляции; файл служит навигации, не создаёт новую границу доступа.
- Начинай с конкретных данных и работающих преобразований. Существующий код уже даёт
  материал; сначала найди место реальной связанности/изменения, затем выделяй границу.
- `cmd`, `internal`, `app`, `business`, `foundation` — варианты раскладки. Ardan service —
  пример, а не стандарт Go. `internal` имеет ограничение импортов языка, `pkg` — соглашение.
  При переезде проверь внешних потребителей, generated code, imports, build/CI и docs.
- Функция принимает только то поведение и данные, которые ей нужны. Общая структура
  `System` или dependency bag не полезна, если скрывает зависимости одного вызова.
- Различай wire DTO, предметные значения и SQL-проекции, когда их семантика различается.
  Не дублируй одинаковые модели ради трёх слоёв и не теряй NULL/empty при объединении.
- Exported API проектируется для пользователей. Unexported helpers можно проверять
  напрямую, когда это полезно; тесты не должны заставлять публиковать внутреннюю кухню.

## Интерфейсы и generics

Обоснования интерфейса: caller подставляет реализацию, поддерживаются разные механизмы
или обнаружена конкретная изменяемая зависимость. Обычно интерфейс объявляет потребитель,
конструктор реализации возвращает конкретный тип. Не превращай «обычно» в запрет интерфейсных
фабрик: стандартная библиотека и существующий внешний контракт могут требовать другого.

Проверяй подозрительные случаи: интерфейс целиком дублирует методы единственного типа;
экспортирован интерфейс, скрыта реализация, но замена не нужна; интерфейс можно удалить
без изменения пользования API. Наличие одного production adapter само по себе не дефект.
Узкий fake для воспроизводимого отказа допустим, но mock не доказывает реальный протокол.

Для generics сначала найди одинаковый алгоритм/контейнер и различающиеся типы данных.
Если нужны только методы, обычный интерфейс может быть точнее. Если все данные одного
типа, concrete API проще. Используй подходящие стандартные generic packages в поддерживаемой
версии Go, не пиши свой framework. `~T`, constraints и inferred type arguments проверяются
компилятором проекта; generics не дают структурное наследование или произвольный доступ к полям.

Embedding выбирай для осмысленного продвижения поведения, не для имитации inheritance.
Явное поле часто лучше, если promotion случайно расширяет внешний method set.
Getter/setter может защищать инвариант или синхронизацию; механическая обёртка поля обычно
не нужна. Не вводи универсальный запрет на getters или смешанные receivers по одной цитате.

## Владение и семантика

Для изменённой модели/границы выясни: кто создаёт значение, кто меняет, кто ещё хранит
ссылку, когда заканчивается использование и когда разрешены reset/reuse/release.

- Go передаёт значения, в том числе адреса. Struct copy с pointer/map/slice полями
  остаётся shallow copy. Slice header copy не копирует backing array.
- `append` может сохранить backing array или выделить новый. Capacity restriction
  предотвращает некоторые append-aliasing эффекты, но не изолирует существующие элементы.
  `copy` и slice clone не делают вложенные maps/pointers независимыми.
- Value semantics подходят безопасно копируемым значениям; pointer semantics — общей
  идентичности, мутациям или некопируемым ресурсам. Mutex/atomic/WaitGroup и содержащие
  их структуры не копировать после начала использования. Receiver выбирается по смыслу,
  не по правилу «указатель быстрее». Method value может захватить копию receiver.
- Нулевая map допускает чтение, len, range и delete; запись требует инициализации.
  Нулевой slice можно append-ить. Nil channel блокирует send/receive. Различай эти случаи.
- Nil/empty, отсутствие ключа/zero value и typed nil в interface — разные состояния.
  Для nullable полей сохраняй их внешний контракт.
- Строки могут содержать произвольные байты. UTF-8 validation нужна по контракту;
  byte length, rune count и grapheme count различаются.
- Тип/alias и преобразование не доказывают проверенность значения. Используй новый
  тип, если API реально устанавливает нужный инвариант; учитывай возможность zero value.

Производительность копирования, escape/inlining и boxing зависит от компилятора и кода.
Не обещай stack placement по одному `return value`, heap по одному `&value`, обязательную
аллокацию интерфейса или конкретный коэффициент роста slice. При необходимости измерь.

## Ошибки и частичные результаты

Возвращай `error`, не указатель на concrete error как альтернативу nil. Сохраняй классификацию
и unwrap-контракт; `fmt.Errorf` с `%w` / `errors.Is/As` применяются по принятой семантике API.
Публичное wrapping может раскрыть зависимость, поэтому не меняй его незаметно.

Контекст ошибки должен помогать выбрать retry, отказ, компенсацию или shutdown. Не парсить
строку ошибки для этих решений. Не возвращать успех за пустой результат по случайному `nil`.
У batch/I/O API проверь обработку одновременно результата и ошибки, индексную привязку и
неизвестный исход. Timeout не всегда доказывает, что внешнее действие не произошло.

Логирование и окончательное решение держи на осмысленной границе; промежуточный слой обычно
добавляет безопасный контекст и возвращает ошибку. Учитывай redaction, PII и credentials.
Новый error code, другой порядок проверок и stricter parser — изменение поведения, не косметика.
