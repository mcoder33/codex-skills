# Дашборды Grafana

Вход: ссылка/UID дашборда или JSON и желаемое изменение; для нового — назначение экрана и проект. Если вход неполный, сначала найди доступные факты в контексте проекта.

Сделай экран, который отвечает на вопросы своей аудитории и не обещает больше, чем подтверждают данные. Сохраняй выбранные пользователем Grafana, источники и границы поручения.

## Начать с задачи и живого состояния

- Определи аудиторию и ключевые вопросы экрана из поручения и контекста. Для узкой правки не начинай заново продуктовый опрос. Спрашивай только о существенной неизвестности, которую нельзя установить чтением.
- Для существующего дашборда прочитай актуальные JSON, UID, версию, папку, переменные, ссылки, datasource и запросы. Сохрани локальный baseline для сравнения и восстановления. Для нового сначала проверь, нет ли уже подходящего экрана.
- Исследуй доступные инструменты и их схемы во время исполнения. Используй проектный контекст, затем реальные поля, labels, примеры и свежие timestamp источников. Конфигурация подключения сама по себе не доказывает наличие данных.
- Предпочитай поддерживаемые существующие источники. Если сигнала нет, обозначь недостающий сбор или доступ. Другой уже разрешённый канал допустим в пределах поручения, если его данные подходят и новые зависимости явно учтены. Навык не разрешает менять инфраструктуру, открывать порты, разворачивать коллектор, обходить авторизацию или создавать тестовые бизнес-события.

## Выбрать нужную глубину

- При изменении состава экрана, запросов или интерпретации метрик прочитай [Смысл метрик и дизайн](references/design-and-metrics.md). Там же правила времени, области фильтров, Kafka и повторяющихся снимков состояния.
- При работе с dashboard JSON, transformations, datasource query API или renderer прочитай [Механика Grafana](references/grafana-mechanics.md). Это версионные наблюдения, а не постоянный API-контракт.
- Для панелей PostgreSQL-репликации и миграции прочитай [PostgreSQL: границы сигналов](references/postgresql-migrations.md).
- Перед сохранением и сдачей прочитай [Проверка и обновление](references/validation-and-update.md). Для поручения только на аудит используй проверки без публикации. При изменении логики выбери применимые [сценарии приёмки](references/acceptance-scenarios.md).

## Рабочий результат

Согласуй название и единицы каждой изменяемой метрики с её источником, объектом счёта, окном и агрегацией. Различай измеренный ноль, отсутствие данных, неизвестное и устаревшее значение. Проверяй смысл на исходных значениях, затем запрос, затем видимый результат; HTTP 200 не заменяет ни одну из последних двух проверок.

Выстрой визуальную иерархию под вопросы аудитории. Выноси специализированные детали на второй уровень, сохраняя доступ к необходимым действиям. Не задавай фиксированное число карточек, графиков или секций для всех задач.

Обновляй существующий UID и URL, учитывай текущую авторизацию из диалога. Перед записью перечитай версию; при конфликте сравни изменения и пересобери правку, не применяй слепой overwrite. Не создавай постоянных дублей или временных дашбордов без необходимости. Редактирование дашборда не требует перезапуска приложения.

В ответе дай ссылку или путь к результату, кратко объясни изменения и границы интерпретации. Укажи, что проверено на данных и в отображении, а что осталось непроверенным. Не выдавай работу renderer/API за доказательство бизнес-результата.
