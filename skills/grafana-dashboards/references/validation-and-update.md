# Проверка и обновление

## Проверить настолько, насколько требует изменение

Для переименования достаточно проверить смысл подписи и затронутый render. Изменение запросов требует проверки источника и агрегации; изменение общего layout — обзора экрана и затронутых деталей. После успешных достаточных проверок не повторяй их без новых изменений или открытой причины.

1. Сверь изменяемые значения с ограниченной выборкой источника: свежие timestamp, объект счёта, cardinality, фильтры, единицы, окно и агрегация. По возможности проверь один результат вручную или независимым запросом.
2. Выполни запросы панелей в нужном временном диапазоне. Проверь не только HTTP status, но ошибки, frames и типы полей. Ожидаемое NoData объясни контрактом; не исправляй его автоматически через fill(0).
3. Проверь видимый результат: общий экран в релевантном viewport и изменённые панели/таблицы, их titles, units, legends, timestamps, пустые и неизвестные состояния. Реальное изображение или UI-проверка ловят ошибки transformations, которых не видно в ответе query API.
4. Для изменённой логики состояний проверь normal, empty, stale, unknown и reset, если они применимы. Для последних снимков включи переход good → bad/missing fields: новая ошибка должна вытеснить старое значение даже без необязательных числовых полей. Используй ограниченные исторические диапазоны или локальные synthetic frames/fixtures, не создавай события в боевой системе. Если состояние нельзя проверить, явно оставь его непроверенным.

Для алертов различай отсутствие активных проблем и отсутствие наблюдений. Пустую таблицу можно подписать «Активных алертов нет» только при независимом подтверждении свежести и покрытия ожидаемых объектов; иначе показывай unknown/stale. Общий heartbeat не подтверждает наличие каждой базы или службы. Для завершившихся одноразовых задач сверяй ожидаемый жизненный цикл: `inactive` после успешного завершения может быть нормой.

При изменении запросов, переменных или текущего состояния используй подходящие [сценарии приёмки](acceptance-scenarios.md). Сценарий, разобранный по инструкции, не называй исполненным на Grafana. Разделяй проверку синтетической выборки, query frames, render и независимый поведенческий прогон навыка.

Набор скриншотов выбирай по изменению: не требуется рендерить каждую неизменённую панель. Если UI/renderer недоступен, сохрани JSON и честно укажи ограничение; API-проверку не называй визуальной.

## Сохранение и восстановление

- До изменения сохрани baseline JSON с UID, version, folder и временем чтения в локальном приватном артефакте. JSON тоже может содержать чувствительные данные; не публикуй его без проверки содержимого.
- Используй уже данное разрешение на обновление. Поручение на аудит или подготовку JSON само по себе не разрешает публикацию. Если запись не разрешена, доведи локальную правку и проверки до reviewable результата перед запросом разрешения.
- Обновляй прежний UID/URL. Перед записью перечитай текущую версию, при конфликте разберись в изменениях; не затирай чужую работу. Не создавай лишний постоянный дубликат. Необходимый временный артефакт учитывай и удаляй в пределах разрешённого scope.
- После записи перечитай дашборд, сравни затронутые поля и проверь опубликованный результат. Восстановление baseline — тоже запись: оно должно учитывать текущую авторизацию, версию и параллельные изменения, а не быть слепым автоматическим rollback.

## Если для метрики действительно требуется изменение коллектора

Этот раздел не расширяет поручение. Сначала установи, что изменение сбора разрешено отдельно или явно входит в задачу. Отсутствие метрики само по себе не даёт права разворачивать новый сервис или выдавать ему admin credentials.

Проверь dry-run/config и реальный runtime parser на представительном входе. Например, Ruby Logstash JSON filter может дать `BigDecimal` для дробного числа, тогда как обычный fixture через JSON parser даёт `Float`: синтетический тест не ловит runtime drop без совпадения типов. Проверь числовые края и последующий фактический выход с timestamp.

Ограничь тело ответа, объём/число файлов, память и retention; настрой rotation по эксплуатационному контракту. Сохрани Filebeat input IDs, fingerprints, registry и очереди, чтобы изменение сбора не вызвало повторное чтение или потерю позиций. Не меняй инфраструктуру и не перезапускай приложение ради редактирования дашборда.

## Если работа делегируется

Следуй применимым правилам команды; навык не вводит обязательную делегацию или фиксированную модель. Контракт исполнителя должен содержать цель аудитории, изменяемые файлы/UID и ownership, baseline, допустимые операции, ограничения данных, ожидаемые артефакты и доказательства. Отдельно укажи запрет на чужие изменения и границу публикации.

Выбирай проверяющего с доступными инструментами для нужного вида проверки. Проверяющий должен видеть реальные запросы/frames и render, а не только отчёт «HTTP 200». Если ограничения роли запрещают Grafana или просмотр изображений, структурное ревью JSON остаётся полезным, но переданные автором доказательства не становятся независимым визуальным аудитом. Явно раздели собственные проверки, полученные свидетельства и непроверенное.
