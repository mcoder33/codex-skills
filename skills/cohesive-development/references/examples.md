# Примеры границ и контрпримеры

Это ориентиры для решений, не шаблоны обязательной архитектуры.

## Завершённость зависит от обещания

- `isEligibleForDiscount(order)` завершает проверку права на скидку. Применять
  её не обязан. `applyDiscount`, которое только проверило право, не завершено.
- `openReadOnlyFile(path)` может вернуть открытый handle с явной обязанностью
  caller закрыть его. Завершённость приобретения ресурса не означает его закрытие.
- `buildDraftOrder` может создать допустимый draft без оплаты. Имя и модель
  состояния объясняют, что завершено. `preparePaymentRequest`, оставляющий
  обязательные body/headers для скрытого patch caller, обещает лишнее.
- `buildBaseLead` может завершать базовую проекцию до отдельной attribution,
  если результат полон именно как base и следующий шаг явно назван.

## Один уровень и маленькие функции

- `subtractBusinessDays(date, count)` может быть коротким содержательным правилом.
- `callJSONUnmarshal` без предметной роли/адаптации только меняет имя библиотеки;
  краткость не даёт ему автоматической ценности.
- `encodePartnerPayload` может быть маленьким adapter с точным контрактом
  escaping/precision/newline: настройки завершённого внешнего представления
  имеют самостоятельный смысл.
- Короткий `processOrder` не улучшает структуру, если `processDetails` скрывает
  прежнее смешение бизнес-решений, SQL и HTTP. Проверяй и детей.
- Литерал DTO с переносом полей и именованными преобразованиями может целиком
  находиться на уровне mapping. Разбиение на `setField1` и `setField2` не требуется.
- Внедрение десяти helpers, новых классов или сокращение строк само по себе
  ничего не доказывает. Открытие другого файла не является штрафом.

## DDD и контекст

- Проверка «этот snapshot пригоден для attribution» не запрещает partial
  snapshot в geo-lookup или другом сценарии. Название validator указывает scope.
- `validSnapshotHeader` не обещает freshness, если сроком жизни управляет reader.
- DTO отправки может быть сложным, но это не основание объявить его агрегатом.
  Граница агрегата требует реальных правил согласованности.
- Формат source ID — правило внешнего контракта; оно не обязательно является
  доменной идентичностью. Не объединяй разные правила лишь из-за одинакового типа.
- Closure of Operations у Evans относится к замкнутости типов операций;
  это не синоним требования «полностью завершить обещанную работу».

## Объём и режим

- «Исправь подпись кнопки» → локальная правка и соразмерная проверка. Навык не
  требует нового model review, исследования литературы или аудита всего UI.
- «Разбери и доработай всё приложение» → карта всех значимых областей и
  итерации по ней. После исправления одного parser задача остаётся открытой,
  пока остальные области не рассмотрены.
- «Примени все изученные принципы к parser» → все применимые критерии в parser;
  слово «все» не разрешает менять storage и deployment.
- «Только оцени diff» → находки без изменения кода и без публикации комментариев,
  если публикация отдельно не запрошена.

## Сохранение поведения

Для рефакторинга parser новый EOF-check, trim, float64 round-trip или изменение
порядка ошибок могут быть регрессией даже при намерении сделать «чище».
Characterization такого контракта проходит до/после. Для поручения исправить
тот же parser новый тест, напротив, должен выявлять конкретную исходную ошибку.
Не сохраняй дефект, который пользователь явно поручил исправить.
